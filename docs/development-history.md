# Development history

[Deutsche Version](de/entwicklungsverlauf.md)

This document records how HostRename came to be. It is deliberately kept out of the README, which is pure operations documentation.

The early development happened outside this repository (in chat sessions and a Linux sandbox with mocks). There is therefore no commit history before 3 November 2026. Everything up to version 1.1.9 is reconstructed from the hand-over notes (`CLAUDE.md`), the change table in the README and the file dates of the delivered package.

## Phase 1 – Building the GPO solution (up to version 1.1.4)

Goal: rename domain-joined Windows clients automatically according to a naming template, without a password in the script.

Results:

- **Client script** `Invoke-HostRename.ps1`: runs as a scheduled task under SYSTEM and renames the computer and its AD object with `Rename-Computer`. It is idempotent and logs to a central CSV on a share, falling back to `pending.csv` when the share is unreachable. Exit codes: 0, 3010, 1, 2, 4, 5.
- **Naming templates** `{Name}` and `{Serial}` with length specifiers (`{Serial:-8}`), plus prefix and suffix. Rules for names that are too long (`TruncateEnd`, `TruncateStart`, `Skip`). A *future ID* derived from the MachineGuid replaces unusable or duplicate serial numbers.
- **Setup script** `Prepare-HostRename.ps1`: creates and removes the share, the AD delegation to SELF (8 rights, compared by SID) and the GPO. The GPO uses GPP Files and a GPP Scheduled Task, with the XML generated by hand. An optional cleanup GPO is available.
- **Cleanup** (`-Cleanup`): flushes the logs first, then sets the marker, then removes the task and the script. If log delivery fails, cleanup is deferred (`CLEANUP_DEFERRED`).
- **Pester tests** in three levels: Local (no AD), Dc and Client.

Lessons from this phase (detailed in `CLAUDE.md`, section "Pitfalls"):

- The delegation needs *Reset password* and *Account Restrictions*. Without them the rename fails with "Access denied".
- The NTFS right *Read attributes* (`RA`) is required on the log folder.
- On German clients the task account must be `SYSTEM` or its SID, never "NT AUTHORITY\System" (event 1085).
- `#Requires` must come after the comment-based help.

## Phase 2 – Stabilising the task start (versions 1.1.5 to 1.1.9)

Problem: in the pilot the scheduled task did not reliably start after a reboot.

Findings:

- With the GPP action *Update*, the task did not start after a reboot. The plausible but unproven cause is that the GPO rewrites the task at boot, after the boot trigger has already fired. The task action was therefore switched to **Create**.
- GPP Files with *Update* failed to overwrite the file (event 4117, `0x50`), so the file action is now **Replace**.
- A `<Delay>` in the registration trigger breaks the GPMC HTML report ("Unknown error"). This was shown with a candidate test (`tools/Test-GpoReport.ps1 -Candidates`). The registration trigger now has **no delay**.

Version **1.1.9** (30 October 2026) combines this: registration trigger without delay, boot trigger + 5 minutes, GPP action Create, no daily trigger. It adds the switches `$RegistrationTrigger` and `$RepeatInterval`.

Pilot status (Windows 11, German system language): the owner confirmed that **everything implemented works**. This covers the delegation, the rename, the language-independent task account, Replace, self-deletion, log delivery and cleanup, the task start in the 1.1.9 construction, appending to the central log with the setup's permission set, the Dc and Client tests, the GPMC report, the item-level-targeting roundtrip and the cleanup GPO.

## Phase 3 – Planning ACMP deployment (3 November 2026)

Situation: about 700 clients, about 90 % of them notebooks. Away from the office they connect over DirectAccess; in the office they use EAP-TLS WLAN with computer certificates. Deployment is to move to ACMP.

The draft `docs/ACMP-Umsetzungsplan.md` identifies the central risk. After a rename, the device's certificate no longer matches an account (strong mapping, KB5014754). The WLAN then fails until a new certificate has been issued, so renaming must only happen over LAN cable or DirectAccess. Building blocks: a network gate, an ACMP mode in the client script, certificate renewal and an ACMP client command.

## Phase 4 – Repository and version 1.2.0 (from 3 November 2026)

- Repository created on GitHub with an MIT license. The generic scaffolding (README, templates, CI) was merged first ([st03psn/HostRename#1](https://github.com/st03psn/HostRename/pull/1)).
- Imported the 1.1.9 package as the baseline. The project's conventions take precedence over the scaffolding: files stay in the repository root, LF line endings, UTF-8 with BOM.
- Decisions taken by the owner:
  - English is the primary language for scripts and documentation; German versions exist as an alternative.
  - GPO and ACMP are alternative deployment methods.
  - Allowed paths for renaming: LAN and DirectAccess.
  - Local logs in ACMP mode go to `C:\ProgramData\HostRename`.
  - The central CSV log is kept as an option.
  - Old certificates are only removed with a switch.
  - Device tests are part of the test phases instead of a precondition.
- Work for 1.2.0 is tracked in [roadmap.md](roadmap.md).

## Phase 5 – Wrapper, simulation, restructure and releases (3 November 2026)

- **Review fixes:** safe disabling of the central log (`''`, blank and non-absolute paths), a hardened ACMP log folder (owner and reparse-point check, protected ACL) and refusal of a 32-bit process on 64-bit Windows.
- **Rollout documentation:** ACMP rollout process and run verification (ACMP tests AC-A to AC-D), EN + DE.
- **End-to-end simulation** (`HostRename.Simulation.Tests.ps1`): copies the real scripts flat into a simulated ACMP cache and runs them with the state-check and status snippets taken from the documentation (registry in memory, CIM, AD, network and certificate store mocked). Changed afterwards: permanent errors (2, 4, 5) no longer lead to endless retries (the state check ends with `phase=permanent` until the value `LastExitCode` is removed), and the cleanup events also go to stdout. Under Windows PowerShell 5.1, .NET Framework's X509 `GetNameInfo` returns the subject CN instead of the first SAN DNS name, so the test checks the SAN directly (the scripts parse the SAN themselves and were not affected).
- **ACMP wrapper** `Invoke-AcmpHostRename.ps1`: runs the whole Client Command flow in one script run per ACMP invocation by calling the unchanged scripts in-process; the Client Command only reacts to 3010 and 20. The simulation covers it with cases W1–W9. A **starter kit** (EN + DE) hands the first ACMP test to a tester who does not know the project; the tester determines the environment values.
- **Restructure:** core and GPO stay in the root; tests of the core in `tests/`, tool-neutral building blocks in `components/`, everything ACMP in `deployments/acmp/`, cross-cutting documents in `docs/`. The ACMP release package is flat, so the wrapper looks for its scripts in its own folder first and falls back to the repository layout.
- **Website** (`site/`, EN + DE) published through GitHub Pages.
- **Releases:** a manual release workflow builds one ZIP per file list (`gpo`, flat `acmp`; legacy single list for v1.1.9). Lesson: the workflow token gets HTTP 403 when it has to create a tag on an older commit, and for v1.1.9 (commit `6605dc8`) even creating the draft release failed. The workflow therefore creates drafts by default, accepts an existing tag that points to the source commit and completes a release the owner published by hand. The owner created the v1.1.9 tag through a helper branch in the web UI. Published: **v1.1.9** (latest full release, pilot-confirmed GPO solution, German) and **v1.2.0** (pre-release, English, GPO and ACMP packages).
- Still open: the device tests (T3); nothing new in 1.2.0 has run on a real device or in ACMP.
